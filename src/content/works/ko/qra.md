## 무슨 문제였나

흩어져 있는 컴퓨터들을 웹에서 한눈에 관리하고, 브라우저만으로 원격 화면을
보고 조작하고 싶었다. 기존 원격 데스크톱 도구는 장치 1:1 연결 중심이라
관리자 관점이 없다 — 그룹, 권한(RBAC), 세션 이력, 감사 로그 같은 것들.
"장치에 붙는 도구"가 아니라 "장치들을 운영하는 플랫폼"이 필요했다.

## 어떤 접근을 골랐나

컨트롤 플레인과 미디어 플레인을 분리했다. NestJS 서버는 인증·권한·세션
상태 머신·시그널링만 담당하고, 화면과 입력은 WebRTC로 브라우저-에이전트가
직접 주고받는다 — 영상이 서버를 통과하지 않으니 서버가 가벼워지고 지연도
준다. 콘솔은 Next.js, 에이전트는 Rust(Windows 서비스 + 사용자 세션 Helper
분리). 프로토콜과 세션 전이표는 공유 패키지에 Zod 스키마와 데이터로 박아서
"계약이 곧 코드"가 되게 했다. 개발 환경은 Docker 없이 embedded PostgreSQL로
돌아가게 했고, mock 장치 30여 대를 등록하는 시뮬레이터로 서버 로직을
검증했다. 에이전트 자동 업데이트는 Ed25519 공개키를 빌드 시점에 박아
서버조차 신뢰하지 않는 서명 검증으로 갔다.

## 뭐가 안 됐나

재연결 기능은 e2e 테스트 43건을 전부 통과하고도 실기에서는 전혀 동작하지
않았다. 테스트가 검증한 것은 서버의 상태 전이와 토큰 규칙이었고, 실제로
깨진 곳은 그 사이를 잇는 전송 계층이었다. 이후 실기 검증이 이 프로젝트에서
가장 값진 습관이 됐다 — 실제 장비에 붙여서만 서버 버그 3건, 조용히 실패하던
결함 3건, 오디오를 켜면 화면이 사라지는 회귀 1건을 찾았다.
오진도 있었다. 간헐적으로 멈추는 e2e를 keep-alive 소켓 문제로 진단하고
정리 코드를 넣었더니 다음 실행이 통과해서 고친 줄 알았다 — 간헐적 실패였을
뿐이다. 실패 출력을 끝까지 읽고서야 동적 import 데드락이 원인임을 알았고,
테스트 프로세스를 분리해서 해결했다. 간헐적 실패는 한 번의 통과로 반증되지
않는다.
파일 전송은 업로드·다운로드가 완벽했는데 감사 로그만 0건이었다.
"되는가"와 "남는가"는 다른 질문이고, 후자는 보러 가지 않으면 드러나지
않는다. 덤으로 Docker Desktop이 이 PC에서 아예 기동하지 못해 검증 환경을
WSL2에 직접 꾸리는 우회도 있었다.

## 결국 어떻게 됐나

qra.qjins.com에 라이브. 브라우저에서 실제 Windows 화면을 보고 마우스·
키보드로 조작하며, 적응형 품질·오디오·클립보드·파일 전송까지 실측을
마쳤다. 이 사이트의 서비스 카드에 걸린 첫 서비스가 됐고, "테스트 통과"와
"실제 동작"의 간극을 좁히는 실기 검증 요령은 다음 프로젝트로 가져갈
가장 큰 자산이다.
